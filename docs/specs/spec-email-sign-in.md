# Spec: Email Sign-in

> Stage: Draft — awaiting review. The implementation plan will follow in `docs/specs/prd-email-sign-in.md`; this file holds the problem, scope and decisions.

---

## Problem Thesis

GitHub is the only way to sign in, so the people most likely to be told about the site, friends sent its link by text, cannot use it unless they have a GitHub account and are willing to use it here. Adding another third-party identity provider would only move the problem: some people have no account with it either, and it would still make a third party the gatekeeper to the site. A player should be able to sign up with nothing but an email address they control, on their own, from the link.

---

## Current State

- **GitHub is the only Auth provider enabled** on the hosted project (`architecture.md` §13). The Email provider is off because, left on, anyone holding the publishable key could create a password account through `/auth/v1/signup` with no UI involved. "Allow new users to sign up" is on, which is what lets first-time GitHub users in.
- **Sign-in is a form-invoked Server Action** (`signInWithGitHub`) that redirects through Supabase to GitHub and back to `/auth/callback`. Every Auth call runs on the server; the browser Supabase client is imported nowhere, so Supabase records the server's address, not the visitor's (Privacy FR-2). The CSP's `form-action` names the Supabase project and GitHub, the hosts that submission redirects through.
- **The site sends no email.** `privacy@` and `contact@arcanaeum.app` are Cloudflare Email Routing rules, which only receive, and no DMARC record is published (`architecture.md` §13). Supabase's built-in sender on the Free plan sends 2 messages an hour, only to members of the project's team, with no delivery guarantee, so it cannot serve users.
- **The header** shows a name from the session's `user_metadata` (`getDisplayName`, which prefers `user_name`, then `preferred_username`, `full_name` and `name`) and the GitHub avatar (`avatarUrlFor`). With none of those keys, `getDisplayName` falls back to the part of the email address before the `@`. `user_metadata` is writable by the user through `PUT /auth/v1/user`, and by whoever signs an address up, which is why `avatarUrlFor` accepts only GitHub's avatar host; the name is not checked the same way. Sign-out ends this browser's session only.
- **The privacy notice and request procedure assume GitHub**: what is collected is listed as GitHub's profile fields, Privacy A2 states GitHub stays the only provider, and `docs/privacy-requests.md` falls back to confirming a requester through their GitHub account.
- **The local stack differs from the hosted project**: `supabase/config.toml` has the Email provider on and email confirmation off.

What was established while investigating, and is the reason for several decisions below:

- **Supabase cannot turn passwords off while the Email provider is on.** There is no such setting in Supabase Auth's configuration, and the CLI's `[auth.email] enable_signup` (v2.119) is the switch for the whole Email provider, not for sign-ups through it. With email sign-in enabled, `/auth/v1/signup` always accepts a password, and a signed-in user can add one through `PUT /auth/v1/user`, whatever the app's own UI offers.
- **That allows an account to be taken over before its owner signs up.** Confirmed on the local stack on 2026-10-05 (Supabase Auth v2.195.0, email confirmation on, as on the hosted project): an attacker signs up the owner's address with a password of their choosing; the account waits unconfirmed and the password is refused; when the owner later asks to sign in by email, Supabase sends them "Confirm your email address" for that same account, and once they follow it, the attacker's password returns a working session. A session is enough to use the app as the owner — the session cookie holds nothing but the tokens — and lasts, since the owner has no way to see or remove the password.
- **Clearing the password closes it.** In the same test, a trigger setting `auth.users.encrypted_password` to null on every insert and update made the attacker's password, a blank one, and one the owner later added through `PUT /auth/v1/user` all fail with `invalid_credentials`, while a new sign-up, a second sign-in and a token refresh still worked. Supabase Auth refuses a password sign-in outright when the stored password is null or empty, before comparing anything, and no input hashes to null.
- **The password is not all the attacker leaves behind.** Sign-up stores whatever `user_metadata` the caller sends, twice: on the new user row, and in the new email identity's `identity_data`, which Supabase then copies back onto the user row in the same transaction (`signup.go`, `RemoveUnconfirmedIdentities`). On the email path Supabase later confirms the existing account without changing it ("do not update the user"), so a name planted at sign-up survives the owner's confirmation, in both places. GitHub sign-in onto an unconfirmed account is handled differently: Supabase clears that account's password, replaces its `user_metadata` with GitHub's and removes its other identities, to prevent pre-account takeover (`RemoveUnconfirmedIdentities`, read in Supabase Auth's source, not yet tested here).
- **A sign-in email carries one token, as a link and as a code.** Supabase's default templates put the link (`{{ .ConfirmationURL }}`) in the message, and a code (`{{ .Token }}`) can be added beside it, but both spend the same token: whoever opens the link first, including a mail scanner, uses up the code. A first sign-in is sent with the "Confirm signup" template and a later one with "Magic Link" (the local test's "Confirm your email address" and "Your sign-in link"); a code verified with `type: 'email'` is checked against both, so one form serves both. The same check also accepts a password-recovery token, and `/auth/v1/recover` stays public once the Email provider is on, so the "Reset Password" template is a third way to receive a sign-in, sent from the same domain against the same email cap; "Change Email Address" can be triggered by any signed-in user for their own account. New Free-plan projects cannot change templates on Supabase's built-in sender since 2026-06-03; with custom SMTP they can.
- **Supabase Auth's per-IP rate limits are shared by every visitor.** These are Auth's own limits, on its endpoints only — sign-up, requesting and verifying codes, password reset, token refresh — not a limit on Supabase requests in general: data queries go through the Data API, which has no per-IP limit. Because every Auth call runs on the server, Auth sees the server's addresses rather than one per visitor, so the limits on requesting and verifying codes (30 requests per 5 minutes each) are a single budget for the whole site, which one visitor hammering the site's form could spend for everyone. Someone calling Supabase directly spends their own address's budget, not the site's. The token refresh each signed-in visitor makes about once an hour shares a larger budget, 150 requests per 5 minutes, far beyond this site's traffic. The email cap, by contrast, is one count for the whole project, however it is reached.
- **Leaked-password protection is a Pro-plan feature**, and **CAPTCHA** (hCaptcha or Turnstile) needs JavaScript in the browser.
- **Identities are linked automatically only when the verified addresses match exactly.** An existing GitHub user who signs in with a code sent to their GitHub email reaches the same account; one who types a different address, or whose GitHub email is a `users.noreply.github.com` address, gets a second, empty account.

Pain points:

- Anyone without a GitHub account, or unwilling to use it here, cannot sign in at all.
- Turning on the Email provider as it stands would open password sign-up and the takeover above.
- The site has no way to send email from its own domain.

---

## Desired State

1. A visitor can sign up and sign in with an email address alone, by entering a code the site emails to them. No password exists at any point, for any account.
2. GitHub sign-in carries on as today, beside it.
3. Sign-up is open: anyone with the link can create an account, with no invitation.
4. Sign-in email comes from the site's own domain, passing SPF and DKIM aligned with it, under a published DMARC policy.
5. A new email user meets the same first-login setup as a GitHub user (Profiles FR-4).
6. A **Sign in** link in the header opens `/login`, which offers both ways in — a **Sign in with GitHub** button and an email field — and either one returns the user to the page they started from.
7. A signed-in user can sign out of every device at once.

"Good" looks like: a friend gets a text with the link, taps **Sign in**, types their email address and taps **Send code**. A message from Arcanaeum arrives within a minute; they type its eight digits, land on the profile setup, choose private, and are back on the page they started from. Nothing asked them for a password, and nothing ever will. Months later, signed out on a new phone, they do the same again and their marks are all there.

## Constraints

- **No third-party identity provider as the answer** (Decision 1). Email is the provider; GitHub stays as it is.
- **Works without JavaScript**: both steps are plain forms that post and redirect (Decision 11), and every state, errors included, renders in the response.
- **Every Auth call stays on the server.** An Auth call from the browser would put the visitor's own address into Supabase's records, which is a Privacy FR-5 change of its own.
- **RLS stays the authorization model**, and no `security definer` function is added: the password trigger runs as Supabase's own auth role, which needs only `execute` on it.
- **The privacy notice is updated in the same change** that turns email sign-in on (Privacy FR-5).
- **Hosted changes go one at a time, in an order that is never unsafe in between**, with the Email provider turned on last (Decision 15).
- **The Free plan**: no leaked-password protection, no custom Auth domain, no Pro-only Auth settings.

## Requirements

**Must-have:**

- [ ] Sign-up and sign-in by an emailed one-time code, offered beside GitHub sign-in.
- [ ] A `/login` page offering both methods, working without JavaScript, with the header's **Sign in with GitHub** button replaced by a **Sign in** link to it. Both methods return the user to the page they started from. The page says that a different email address means a different account.
- [ ] Open sign-up, with email confirmation on, locally as on the hosted project.
- [ ] No account can hold a password, enforced in the database and covered by database tests that would fail if Supabase changed the column.
- [ ] No email from the site contains a link that signs someone in or changes their account: every template a public endpoint or a signed-in user can trigger — "Confirm signup", "Magic Link", "Reset Password" and "Change Email Address" — carries a code and no link, with the code kept out of the subject and the first line (Decision 12).
- [ ] Unconfirmed accounts whose only sign-in method is email are deleted a day after their last code was sent, and the header never shows anything a sign-up could have planted (Decisions 8 and 14).
- [ ] Sign-in email sent through a custom SMTP provider, from the site's own domain, with aligned SPF and DKIM and a DMARC record that sends reports.
- [ ] The first-login check runs after an email sign-in exactly as after a GitHub one (Profiles FR-4).
- [ ] The header never shows any part of an email address.
- [ ] The email sign-in handlers check `next` themselves, as `/auth/callback` does for GitHub, and refuse a request whose `Origin` is not the site's own (Decision 11).
- [ ] The address waiting for its code kept in a short-lived cookie, never in a URL, so a refresh neither resends the code nor loses the address (Decision 13).
- [ ] Every failure — a wrong code, an expired code, a resend too soon, a refused or rate-limited request — shown in app-written words, never Supabase's text, as `/auth/auth-error` already does.
- [ ] A Vercel Firewall rate-limit rule matching a POST whose path starts with `/login/`, which covers both email handlers, the only place the code-sending and code-checking logic exists, in place before the Email provider is turned on, since Supabase Auth's per-IP limits are shared by every visitor; and Auth's own email cap set low (Decisions 9 and 15).
- [ ] **Sign out everywhere**, beside **Sign out** (Decision 16).
- [ ] The privacy notice, the request procedure and the privacy spec's assumptions updated for the second provider, including: Resend receives the address and the code, and keeps its logs for 30 days, which deleting an account does not remove; open and click tracking stay off; an address typed into the form is stored before it is confirmed, and deleted within about a day if never confirmed; the pending-address cookie; an email-only account can be confirmed only through its mailbox, with no GitHub fallback; a session lasts until it is signed out, everywhere or on that device, or goes unused for about 90 days; the data export never includes one-time tokens, and can include profile data sent when an account was first registered (Decision 14).

**Nice-to-have (out of scope for this spec):**

- Passwords, and the reset flow they need.
- Magic links.
- Passkeys (Supabase beta since 2026-05-28): passwordless and no third party, but WebAuthn needs JavaScript, so a passkey could only ever be an addition to codes.
- Other providers (Google, Discord).
- CAPTCHA.
- Changing one's email address, or linking and unlinking sign-in methods, from the UI.

## Assumptions

- Few users: sign-in email stays far inside the sending provider's free plan.
- The project stays on Supabase's Free plan.
- Profiles M1 ships first, so the first-login check already exists as a helper to call.
- Email sign-in is built and tested on the local stack, where mail is caught locally, and the separate dev project (`architecture.md` §13.3) is set up before email sign-in is turned on in the hosted project, since that is when strangers can first sign up (§13.1).

---

## Success Criteria

1. A person with no GitHub account signs up from the site's link, on a phone, with JavaScript disabled, and reaches profile setup. On the same path, a wrong code, an expired code, a resend requested too soon and a rate-limited request each show an app-written message, and refreshing the code step neither resends the code nor shows the address in the URL.
2. No row in `auth.users` on the hosted project has a password, and an attempt to sign in with one is refused.
3. The confirmed takeover — sign-up with a chosen password and a planted name, then the owner's first sign-in — fails on the hosted project: the password is refused and the planted name appears nowhere on the site.
4. Sign-in email from the site passes SPF and DKIM, each aligned with the sending domain, and DMARC at Gmail, and DMARC aggregate reports arrive at the report address.
5. Linking works in every order: an existing GitHub user who signs in with a code sent to their GitHub email reaches their existing account and collection; an email user who later signs in with GitHub using the same address does too; and an address pre-registered by someone else, confirmed by its owner with a code and then used with GitHub, reaches one account with no password from the pre-registration.
6. With the password trigger installed on the dev project, and then on production before the Email provider is turned on, an existing GitHub user signs in, refreshes and signs out normally.
7. **Sign out everywhere** on one device ends the session on another.
8. The privacy notice describes email sign-in, the sending provider and everything in the privacy requirement above on the day it ships.

| 11  | Where sign-in happens                | **A page of its own, `/login`**, rather than forms in the header: an email field, a code step and their error messages do not fit the header bar, least of all on a phone. **The return path is read when the page loads.** GitHub sign-in finds its way back today from the form's `Referer`, which from `/login` would be `/login` itself, and the header cannot add `?next=` to its link because the root layout never learns the current URL. So `/login` reads the `Referer` of its own page load — the page the visitor came from — passes it through `returnPathFrom` and `isSafeReturnPath`, and puts the result in a hidden `next` field in both forms. **The two email steps are Route Handlers at fixed paths, `POST /login/send-code` and `POST /login/verify-code`,** posted by plain HTML forms, each answering with a redirect: that works without JavaScript, gives the rate-limit rule one stable path to match (Decision 9), and leaves the sign-in logic reachable at those two paths and nowhere else. It is the second exception, after `/auth/callback`, to writes going through Server Actions, and `CLAUDE.md`'s auth section records it in the same change. **How the handlers answer:** (1) **A redirect with status 303**, never `NextResponse.redirect()`'s default of 307, which tells the browser to repeat the POST — against `send-code` that would send a second code and invalidate the first, the failure Decision 13 exists to prevent. (2) **Cookies set as `/auth/callback` sets them**, through the server client's `cookies().set()` before the redirect, so the session and the pending-address cookie reach the browser; a response built from scratch would drop them. (3) **An `Origin` check that fails closed**, since a Route Handler gets none of the origin check Next applies to Server Actions: a missing or `null` `Origin`, or any other site's, is refused, and the comparison is with the public host as `/auth/callback` builds it from `x-forwarded-host` — `request.url`'s origin is internal on Vercel, and a hard-coded production address would refuse local sign-in. (4) **Failures redirect with a fixed code**, never free text, mapped to app-written wording as `/auth/auth-error` already does, since anyone can write that URL. GitHub sign-in stays a Server Action. **A hidden field can be changed before it is posted**, so the GitHub action and both email handlers check the posted `next` again with the same rule; `/auth/callback` still checks it for GitHub, and the email handlers, which never pass through the callback, check it themselves. `/login` counts as no destination, whether it arrives as the `Referer` after a reload or as a posted `next`, and falls back to `/`, so sign-in never returns to the login page; a visitor who is already signed in is sent on to `next` rather than shown the forms. |
